01

Where it sits

Beside the system it tests. Never inside it.

Your test server already has the app and its databases. Testate docks next to them as one container, and everyone who needs a clean database comes in through it.

02

The loop

Take a state. Break it. Check it out.

A state is a data-only snapshot of every database in a project, taken at one moment. A checkout puts the one you pick back and reports what happened per database.

01 · take

One snapshot, every database

PostgreSQL, MySQL, MariaDB and MongoDB, captured together. It says who took it and what it cost in bytes. HEAD marks where you are.

02 · break

Run the test. Dirty the data.

Edit rows in the grid, load a fixture, or let the suite do its worst. Testate stashes before your first write, so even a hand edit is reversible.

03 · check out

Back in seconds, with a diff

One click or one API call restores the state and reports per database. Compare any two states and drill into the rows that moved.

03

What it does

A reset you can trust, and a record of what moved.

states

Snapshots

Data, not schema. A timeline per project with HEAD marked, one protected starting point, and a quota so the volume never fills without warning.

diffs

Row-level diffs

Two states, or a state against the live database. The summary counts what moved; a table opens to the rows, before and after, and a changed cell opens its value.

grid

The grid

Filter, sort, page by keyset, follow a foreign key into the next table. Turn on write mode and edit with the types the column really has.

imports

Fixtures

Upload a CSV or XLSX, map the columns, dry-run it, then import. Rejected rows come back as a file you fix and send again.

query

Read-only console

Saved queries, so the check you run after every reset stays where you left it instead of in someone's notes.

api

Pipelines

Every screen sits on the REST API. One call resets a database before a test run, and the running instance serves its own OpenAPI contract.

05

Agents

An agent can look. Only a tester token can touch.

Testate speaks MCP. Point Claude or any MCP client at the endpoint with an agent token and it reads schemas, pages rows, runs read-only queries and extracts fixtures. A Guest token has no write path at all. Queries run inside a read-only transaction, and column policies mask values before the agent sees them.

It does not have to be taught how. The first tool it sees is help: how the pieces relate, the order to call things in, and the limits that refuse a call.

Start

              
Running in about a minute.

              

                Run the container. One volume holds the snapshots, the metadata and the
                logs. The container filesystem is otherwise read-only.
              

              

                Sign in. Open localhost:7378 as admin. Testate
                makes you change the password on the first login.
              

              

                Point it at a database. Add an adapter, take a snapshot, break something,
                put it back. Where to aim the host is the one thing that catches people out, so the README
                spends a section on it.
              

            

            

              

              
              
docker run -d --name testate \

              
-p 7378:7378 -v testate-data:/data \

              
-e TESTATE_SECRETS_ACTIVE_KEY="$(openssl rand -base64 32)" \

              
-e TESTATE_ADMIN_PASSWORD=change-me-now-1234 \

              
ghcr.io/pt-perkasa-pilar-utama/testate:1.0.0

              
 

              
curl -s -o /dev/null -w '%{http_code}\n' \

              
localhost:7378/api/v1/health/live

Before you install it

            
What it does not do.

          

          

            

              
Databases go one at a time

              

                Even inside one project, Testate snapshots and restores them in sequence. Each is correct
                alone; the set is not guaranteed to line up. Keep the app idle while it runs.
              

            

            

              
It only resets what you add

              

                An untracked database survives a reset, and Testate cannot warn you, because it has never
                heard of it.
              

            

            

              
Microservices are untested

              

                Every limit above compounds. Stay inside one service and add the rest as read-only
                adapters.
              

            

            

              
It needs a real connection

              

                Firebase, Firestore and DynamoDB hand you an SDK rather than a connection, so they cannot
                be added. Supabase, Neon, RDS and Cloud SQL work.
