# The Logs tier (#37): decisions

Date: 2026-10-10

| # | Question | Decision | Why |
|---|----------|----------|-----|
| Q1 | What shape does Logs take? | The complete fourth tier, `logs`, with log-only engines of its own. The `adapters` table is rebuilt to widen its `kind` and `engine` CHECK constraints. | The user's call. The recommendation was a Logs view on existing adapters first, because tier belongs to the engine and every first source used an existing engine, and because a new engine costs a rebuild of a table eight others reference. The user chose the complete tier. |
| Q2 | Which engines, and how is it delivered? | Logs-tier engines: `logfile` (files over SFTP or S3, a path glob plus a format; pm2 is a preset), `journald` (`journalctl -o json` over SSH), `docker` (Engine API container logs), `loki` (`query_range`, LogQL), `elasticsearch` (`_search` on an index pattern; OpenSearch too), and `ingest` (Q4b). Database server logs (Postgres, MySQL, MariaDB, MongoDB) cannot be Logs engines, since tier belongs to the engine: they are a "Server logs" read on the existing database adapters. OpenTelemetry has no engine: read the backend the collector writes to. #37 is the umbrella; one sub-issue and PR per step: (1) the base: tier, rebuild, logs port, parsers, viewer, agent tool, `logfile` with pm2; (2) `ingest`; (3) database server logs; (4) `journald`; (5) `docker`; (6) `loki`; (7) `elasticsearch`. | Step 1 alone touches the schema, the engine port, the web and MCP; every later engine is one adapter on a settled base, reviewable alone. |
| Q3 | What is a log source, and where does it show? | **Revised, see Q3b.** An adapter with kind `logs` in the `adapters` table (CHECK widened to `database \| storage \| logs`), project-scoped, sealed credentials, netguard on every connect, Inspect's owner rule. Mode is always `read_only` and the switch is hidden: the logs port has no write. A "Logs" sidebar entry beside Storage lists every log adapter in scope (`GET /log-adapters`, scoped like `/storage-adapters`), grouped by project like Storage; an adapter's page is its log viewer. | Storage proved the pattern: same table, sealing, scope rules and its own list. A separate table would repeat sealing, netguard, scope and ownership. |
| Q4 | What does "our protocol" mean? | Testate's wide-event shape (spec 21) as a named format, `testate`: `ts` to time, `level` to level, `service.name` to source; the message built from the request (method, path, status), the job (kind, status) or `error.message`; every other section kept as fields. No transport that reads the Testate host's own disk. | Any app that writes the shape gets the fields. A local-disk transport would let anyone who can add an adapter read the server's files, which netguard exists to prevent. |
| Q4b | A push entry point for integrators? | Yes: the `ingest` engine. Adding an ingest adapter creates its own ingest token, write-only and good for that adapter alone, shown once. `POST /api/v1/ingest/<adapter-id>` with `Authorization: Bearer <token>` takes `testate`-format JSON lines, one or many; body cap 1 MB, 429 above a per-adapter rate. Stored as daily JSON-lines files under `<data>/logs-ingest/<adapter-id>/`, never in SQLite; per adapter a retention in days (default 7) and a size cap (default 1 GB), oldest day removed first. Read through the same logs port. A malformed line is stored, never refused (refined by I3: wrapped as text with the receive time). | The user wants integrators to log to Testate their own way: an endpoint, a file, or a backend. The strongest case against was that Testate becomes a log store with a new write surface; the user accepted that. The ingest-only token keeps the endpoint from reaching anything else; files and retention bound the size and keep SQLite out of it; accepting malformed lines keeps a logging bug from dropping the lines around it. |
| Q5 | Redaction? | Built-in patterns masked for viewers and agent tokens (story 148's audience); testers and admins see raw lines. Patterns: Authorization and Bearer values, `password=`, `"password": "..."`, JWTs, AWS access keys (`AKIA...`), URLs with `user:pass@`, PEM private-key blocks. Each match becomes `***`, and the entry is marked masked. An adapter can add its own regex patterns. Masking runs on the server, before the response. | App logs leak tokens and agents read logs over MCP. One rule for who sees raw data, columns and lines alike. |
| Q6 | How much can one read return? | 200 lines by default, at most 5,000 per request; at most 10 MB read per request, files read from the end; a time window of at most 7 days. An answer cut short names the limit and returns a cursor for the next page back. No read loads a whole file. | A busy log runs to gigabytes; reading from the end under a byte ceiling keeps a request cheap at any size. The cursor pages older lines rather than hiding them. |
| Q7 | Live tail? | Poll with a cursor: "follow" asks for lines after the last cursor every 3 s, up to the line cap, and stops while the tab is hidden. | One read contract for every engine ("after X"), the same one the agent uses, and no connection held open per viewer. |
| Q8 | "Logs during this test run"? | A checkout's page and a job's page get a "Logs during this run" menu listing the project's log adapters; picking one opens its viewer with the window from the job's `started_at` minus 1 minute to its `finished_at` plus 5 minutes (now while it runs). One adapter at a time; no merged view across adapters in #37. | The job row already holds both times, so this is a link with a filled-in filter. A merged view across sources meets clock drift and per-engine paging: its own problem. |
| Q9 | What do agents get? | One MCP tool, `read_logs`: `project`, `adapter`, `from?`, `to?`, `level?`, `text?`, `limit?` (max 5,000), `cursor?`; returns parsed entries (time, level, source, message, fields) and the next cursor, always masked. `list_adapters` already lists log adapters with their tier. Viewer agent tokens and Inspect-scoped tokens may call it. | An agent debugging a failed test needs the window's lines, not a file; one tool on the shared contract serves every engine. |
| Q10 | Log adapters in the Inspect project? | The five read engines are allowed in Inspect under the owner rule; an `ingest` adapter is refused there with `PROJECT_READ_ONLY`. Taken as the recommendation; the user has not objected. | Reading logs is what Inspect is for; ingest stores outside records in Testate, and Inspect refuses every write to Testate's own records (#56 Q4). |

## Step 1: the base and `logfile` (decided 2026-10-10)

| # | Question | Decision | Why |
|---|----------|----------|-----|
| S1 | What is one `logfile` adapter? | One connection (an SFTP host or an S3 bucket) holding a list of named sources, each `{ name, glob, format, patterns }`; format is `pm2`, `json-lines`, `testate`, `syslog`, `plain` or `regex` (with named groups). The viewer picks a source. | A pm2 host runs several apps; one adapter per app would copy the same credential, netguard check and host-key trust into each. |
| S2 | Several files per glob, and multi-line entries? | A source reads every matching file and merges entries by time, newest first; each entry names its file. A line with no timestamp of its own joins the entry above it in the same file. A file counts only when its modified time overlaps the window asked for. | An error and the request before it often sit in different pm2 files; a stack trace split into plain entries is unreadable; a 7-day window should not open every rotated file. |
| S3 | What does "download" give? | The entries matching the current filters and window as JSON lines, parsed and masked exactly as on screen, within the 5,000-line cap. Raw files stay reachable through the Storage menu for those allowed there. | One rule for what anyone sees; a raw download would hand a viewer the tokens the viewer hides. |

Build notes, from the code:

- The rebuild. Migrations run in a transaction with foreign keys on, so dropping `adapters` would cascade into the seven tables that reference it. The runner gains an opt-in: a migration whose first line is `-- testate:foreign-keys-off` runs with foreign keys off, then `PRAGMA foreign_key_check` must return nothing before they come back on (SQLite's documented procedure). The rebuild widens the CHECKs to all six Logs engines at once; the shared `ENGINES` enum grows one engine per step.
- Tail. `FileSource.read` returns the whole file; SFTP and S3 gain a ranged read so a source reads from the end under the 10 MB ceiling.
- Step 1 ships as three PRs under #69: (a) the runner opt-in, the rebuild and the contract (the piece to read line by line, and the one that makes the rest compile); (b) the port, parsers, ranged read, `logfile`, routes and `read_logs`; (c) the web.

Parser rules, stated from how the formats behave (not asked):

- **Untimed files.** pm2 writes a timestamp only when started with `--time` or `log_date_format`. A read in which no line yields a timestamp is read in position order, each line its own entry stamped with the file's modified time, and the answer says `untimed: true` so the viewer can say so. A time window cannot filter such a file.
- **Naive timestamps.** pm2's date prefix and syslog carry no zone (syslog no year): they are read as UTC, and the format's documentation says so.
- **Levels.** `level`, `severity`, `lvl` or `log.level`; pino and bunyan numbers map (30 info, 40 warn, 50 error, 60 fatal); a line from a pm2 `-error.log` with no level is `error`, any other is `info`.
- **Tester regexes are a trust boundary.** The `regex` format and per-source masking patterns are checked at save: they must compile, stay under 200 characters, and hold no nested quantifier. A line is cut at 16 KB before any pattern runs. The ceiling is the lack of a regex timeout in the runtime; RE2 is the upgrade.
- **Globs.** One directory under the connection's root, a pattern on the file name only: no `**`, no `~`.
- **Cursor.** Opaque; per-file byte offsets. "Older" reads up to 10 MB before each offset; "after" reads from each offset to the end and lists the directory again, so a newly rotated file appears. The partial first line of a ranged read is dropped.

## Step 2: `ingest` (decided 2026-10-10)

Q4 and Q4b decide the endpoint, the token, the format, the storage, the retention and the size cap. These are the branches they left open.

| # | Question | Decision | Why |
|---|----------|----------|-----|
| I1 | Where does an ingest token live? | Its own table, `ingest_tokens` (adapter_id, token_hash, prefix, created_at, last_used_at): one active token per adapter, rotated on the adapter page, never on the Tokens screen. | A third kind in `api_tokens` means rebuilding that table under its foreign keys (`write_sessions`), and the Tokens screen would list tokens that do one thing for one adapter. |
| I2 | How do pushed lines become sources? | A line's `service.name` is its source; none goes to `default`. Lines are stored at `<data>/logs-ingest/<adapter-id>/<source>/<YYYY-MM-DD>.jsonl`, so the source list is the folder list and the config declares no sources. The viewer reads with the `logfile` reader over a local file source, format `testate`. A source name keeps `[A-Za-z0-9._-]`, the rest become `_`, cut to 64 characters. | It reuses the merge, the cursor, masking and paging as they are, and a new service appears without an edit. |
| I3 | A line with no `ts`, or not JSON? | The server stamps the receive time. A JSON line with no `ts` gets one. A non-JSON line is stored as `{"ts": <received>, "level": "info", "message": <raw line>, "ingest": {"malformed": true}}`. | A bare text line has no time of its own, so the reader would join it to the entry above (25 §25.2), at the wrong time. Wrapping keeps every line its own entry and still visible. |
| I3a | How does a person find and clear ingested logs? | `testate whereis ingest` prints `<data>/logs-ingest`. "Clear logs" on the adapter page: admin, confirmed, audited. No CLI clear. Deleting the adapter removes its folder. | A CLI delete leaves no audit row and skips the adapter's lock; the page knows which adapter is meant. |
| I4 | The per-adapter rate? | 600 requests a minute per adapter on the existing sliding-minute limiter; 429 with `Retry-After` above it. An admin changes it in Settings, Limits. | A batching client never meets it; a per-line client at 10 lines a second fits. |
| I5 | The size cap is reached? | The write removes the oldest day files until the total fits, never today's. If today alone is over the cap, a push answers 507 `INGEST_FULL` and stores nothing until midnight UTC, a clear, or a higher cap. The daily sweep removes days past retention. | A long run keeps going; a logging loop cannot fill the disk, and the integrator is told. |
| I6 | What does a push answer? | 202 `{ "accepted": n, "malformed": m }`. Body: JSON lines (`application/x-ndjson`); one JSON object is one line. Empty body 400; over 1 MB 413, nothing stored. | An integrator's test can check the count; a logging bug shows as `malformed`, not as silence. |
| I7 | Do backups include ingested logs? | No. They are operational, like Testate's own logs (04, data locations). The backup screen and the docs say so and point at `testate whereis ingest`. | A backup is metadata and blobs; a gigabyte per adapter would swell it. |
| I8 | Create, token, rotate? | "New log adapter" gets a type: "Files over SFTP or S3" (`logfile`) or "Push from your app" (`ingest`: name, retention days default 7, cap MB default 1024). After Create, the token shows once with a copy button and a curl line. The adapter page adds "Rotate token" (tester and up, confirmed, audited; the old token stops at once), "Clear logs" (admin) and edit of name, retention and cap. | A tier is one menu with one "new" button; the token is needed the moment it is shown. |
| I9 | Which day file, and a `ts` in the future? | The receive day (UTC) picks the file, never `ts`. A `ts` after the receive time is clamped to it; the sent value stays as `ingest.sent_ts`. | The reader stops on a file whose modified time is older than the oldest line it kept (25 §25.3): it assumes no line is newer than its file. A fast client clock would hide lines; whole-day files keep retention exact. |
