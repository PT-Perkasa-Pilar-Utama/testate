# The testate CLI (#57): decisions

Date: 2026-10-10

| # | Question | Decision | Why |
|---|----------|----------|-----|
| Q1 | Service scope? | Per user only: `systemctl --user` on Linux, a LaunchAgent on macOS. No `--system` flag. A system-wide service stays the manual README path from #53 (the `DynamicUser` unit). On Linux, `service install` runs `loginctl enable-linger` when it is allowed, and otherwise prints the command, so the service starts at boot. | Matches `install.sh`, which avoids sudo and installs to `~/.local/bin`; `testate update` can then replace the binary without sudo. `--system` would mean copying to `/usr/local/bin`, sudo for every update, and a second unit to keep in sync with `deploy/systemd`. |
| Q2 | Windows, update trust, dashboard notice? | (a) No `service` on Windows in this cut; Windows gets `start`, `setup`, `update` and written instructions. (b) `update` trusts the SHA-256 in `checksums.txt` over HTTPS, the same trust as `install.sh`; Sigstore later, when it can be checked without shelling out to `cosign`. (c) No update notice in the dashboard; only `update --check` and `update` contact GitHub. | A Windows service needs a native wrapper or a scheduled task, a project of its own. Checksums catch a corrupted download; `install.sh` checks no more, so `update` is no weaker than install. The README promises no telemetry. If replacing a running `.exe` fails on Windows, `update` refuses there and prints the manual steps rather than leave a broken binary. |
| Q3 | Where does `setup` write, and how does `start` find it? | Env file `~/.config/testate/testate.env` (follows `XDG_CONFIG_HOME`; Windows `%APPDATA%\testate`). Data `~/.local/share/testate` (follows `XDG_DATA_HOME`; Windows `%LOCALAPPDATA%\testate`). The same paths on macOS. `testate` and `testate start` load `--env-file <path>` if given, else the default env file if it exists, else nothing. A variable already set in the process wins over the file. The unit and the plist pass `--env-file` with the full path. launchd logs to `~/.local/state/testate/testate.log`; Linux uses the user journal. `testate whereis` lists every location and whether it exists; `testate whereis <env\|data\|bin\|service\|log>` prints one path for scripts. The data path comes from `TESTATE_DATA_DIR` in the env file when it is set there. | Process env winning keeps #53 unchanged: the systemd `EnvironmentFile`, pm2's `env` and the container's variables all arrive as process env. The env file sits outside the data directory, so a backup of the data never carries the key (07-security). One set of paths, one set of docs. `whereis` was the user's addition: it answers "where is my config" without reading docs. |
| Q4 | The `.env` autoload? | Build with `--no-compile-autoload-dotenv` and `--no-compile-autoload-bunfig`. The binary reads only what Q3 names. | A stray `.env` or `bunfig.toml` in the folder testate starts from loads silently today, so a project's `PORT` or key leaks into Testate. Anyone relying on a `.env` next to the binary passes `--env-file ./.env`; it was never documented, and v2.0.0 is a breaking release. |
| Q5 | An unknown argument? | Refuse: print `unknown command "<arg>"` and the command list, exit 2. A bare `testate` still starts the server. | A typo never starts a server nobody meant to run. |

Stated from the issue and the code, not asked:

- Commands: `testate` and `start` (the server), `setup`, `service install\|start\|stop\|status\|logs\|uninstall`, `update` and `update --check`, `whereis`, `version` and `--version`/`-v`, `help` and `--help`. Parsing with `util.parseArgs`, prompts with `node:readline/promises`; no new dependency.
- The container runs `bun dist/index.js`; the script path is skipped before parsing, so its arguments stay empty.
- `setup --yes` needs `TESTATE_ADMIN_PASSWORD` in the environment and refuses without it; it never invents a password it would have to print. It never prints the key or the password.
- `setup` on an existing env file keeps the sealing key and asks before changing anything else; with `--yes` it only fills what is missing.
- `update` refuses outside the standalone binary (`bun dist/index.js`, the container), on a Homebrew install (naming `brew upgrade testate`), and where it cannot write the binary. After a swap it restarts the per-user service when one is installed.
- Exit codes: 0 done, 1 failed, 2 wrong usage, 78 configuration refused.
- The one exception to "no `~/Library`": launchd only reads `~/Library/LaunchAgents/`, so the plist is `~/Library/LaunchAgents/io.testate.server.plist`. `service install` creates `~/.local/state/testate` first, because launchd does not create the log directory. The Linux unit is `~/.config/systemd/user/testate.service`.
- `service` and `update` refuse outside the standalone binary: a unit that runs `bun` would be wrong.
- `update` reads releases from a fixed HTTPS URL (`RELEASES` in `cli/update.ts`). Only the unit tests pass another base, a local `Bun.serve` over HTTP; there is no flag or variable that changes it in the field.

## Deferred

| Branch | Reason | Who decides |
|--------|--------|-------------|
| `service --system` | The manual systemd path from #53 covers it | When a user asks |
| `service` on Windows | Needs a native service wrapper or a scheduled task | After v2.0.0 |
| Sigstore verification in `update` | Needs verification without `cosign` | After v2.0.0 |
